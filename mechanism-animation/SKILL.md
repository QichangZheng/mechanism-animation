# 原理动画（mechanism-animation）

把「它是怎么工作的」做成一页分步动画：读者滚一下走一步，每一步只讲一件事，图里的东西按因果顺序一个个出现、移动、消失。

成品参考：`assets/template.html`，模板，自带一个 4 步的小例子（没有缓存 → 加一层缓存），用浏览器直接打开就能看。

## 0. 先判断：该不该做动画

从便宜的往贵的试，前一档讲得清就不往后走：

| 档 | 用什么 | 什么时候够 |
|---|---|---|
| 1 | 直接写字 | 两三句话能说清 |
| 2 | 编号步骤（1. 2. 3.） | 是个过程，但每一步一句话，读者不需要「看见」 |
| 3 | 编号步骤 + 2–3 张定格的静态图（前 / 后对比） | 结构、关系；或过程拆成两三张定格图就能看懂 |
| 4 | 本 skill：分步动画 | 讲的是东西从哪到哪、先后顺序、同一份数据被谁共用、哪一步省掉了什么，**三张定格图还讲不清** |

判据一句话：**把图定格在任意一帧，读者还能看懂 ⇒ 静态图就够；要看到「动」才明白 ⇒ 做动画。**

两条边界：
- **成本**。动画是静态图的好几倍（核对事实、排先后、调时间、自测、来回改）。别人没点名要动画时，先提议、说明为什么前三档不够，对方同意再做；不要默认开工。
- **动画只管「第一次看懂」，不能当查阅材料**：不能扫读、不能搜、贴不进文档。所以页面结尾要有一段「全过程一览」（模板自动生成：每步一行字）；原来的文档保留文字版，再加一个链接指到动画页，不要用动画页替换文档。

## 1. 流程

1. **核对事实**。动画会把错误讲得很生动。画之前把要讲的机制对着代码 / 设计文档 / 论文核一遍，分清「设计上这么说」「代码现在这么做」「别家（论文、默认值）这么做」。拿不准的写「推断，待实测」。
2. **写分镜**（不写代码）。照 [`references/storyboard.md`](references/storyboard.md) 列一张表：每步一行，写清这一步**讲哪一件事**、画面上**依次**出现什么 / 动什么、结束时留下什么、左边那句话。分镜过了下面第 2 节的讲法规则再动手。步数多（> 6 步）或讲法没把握时，先跟提需求的人对一下：**只发那张表加一个要他定的问题**，不要发成一份文档；对方习惯直接看成品的，就直接做。
3. **从模板起**：`cp assets/template.html <产物目录>/<名字>.html`。只改三处：
   - HTML 里的 `<title>`、开头页（`#top`）、图的 `aria-label`、结尾页（`#where`，含页脚的「更新：年月 · 对着哪个版本核的」）——模板里这几处还是示例的内容，逐处换掉；
   - 脚本 **A 段**：`PAGE`、`MODULES`（模块、步骤、文字、每步时长）；
   - 脚本 **C 段**：画面（有哪些对象、每一步怎么动）。
   B1 / B2 两段是引擎，一般不动。写法、小工具、现成套路见 [`references/engine.md`](references/engine.md)。
4. **自测**：`node scripts/check.js <页面.html> <截图目录>`，10 项没有 FAIL（`contain` 在页面没有归属标记时是 SKIP，正常），**再把截图逐张看一遍**：`step-NN`（每步结束）、`mid-NN`（每步走到一半）、`page-NN`（整页）。脚本只能查「停没停住、压没压字、出没出框、字够不够大」，查不了「讲没讲清」。4 步的页面约 1 分钟、12 步约 3 分钟，装依赖和用法见 engine.md 末尾。
4.5 （步数多或讲给外行时）**「第一次看的人」测试**：起一个不知道这个机制、没读过任何资料的子代理，只给它页面每一步的截图，按顺序看一遍，然后凭记忆复述每一步讲了什么、是图告诉它的还是字告诉它的、哪里没看懂。它看不懂的地方是页面的问题，不是它的问题——比自己再看十遍管用。
5. **交付**：把页面（单个 HTML，不依赖别的文件）交给提需求的人。之后每次改完都要重跑自测再交。
6. （内容重要时）**技术核查**：页面定稿后，起一轮只读核查，把页面上每句话、每个数字对着代码和文档逐条核，出一份「错的 / 有误导的 / 不精确的」清单，由提需求的人定改哪些。核查只管事实；讲法好不好，由提需求的人自己看。

## 2. 讲法规则（最重要，都是被打回来之后才学会的）

**顺序**
- **先易后难，先「没问题的情况」再「出问题的情况」**。读者先看到正常是什么样，才看得出问题在哪。例：先讲一台虚机里很多容器共用内存（没问题），再讲换成很多台虚机后每台各存一份（问题），再讲解法。
- **先底层、后上层，一层层出现**。先只有宿主 → 数据从磁盘进宿主内存 → 虚机出现 → 数据进虚机 → 最后才出现里面的程序。不要一开场就把所有框摆好，也不要让程序先出现、数据后到。
- **一步里的几件事有因果就排先后**，不要同时发生。「容器退出」之后，「它的内存空出来」，然后才「还给宿主」。
- **图等滚动停了再出现**，第一步的动画从头播；这些模板已处理，别改坏。

**每一步讲什么**
- **一步只讲一件事**，标题就是这件事（「三个页面各读一次」），不是名词（「读取阶段」）。
- **主线只演实际的做法**。默认值、别家的做法、历史方案，放在这一步的要点里用一句「为什么要专门这么做」带过，**不要单独做成一步**——否则读者以为实际也要先走那一步。（反例：先演「按 2 MB 上报」再演「按 4 KB 上报」，读者问「哪来的 2 MB？到底先哪个？」）
- **看起来一样的两步，读者会以为是同一件事**。两个场景有差别，就把差别画出来（几条箭头汇到同一份数据上、用圈标出共用的那一份），不要只在文字里说。
- **图上出现的每个数字、每个词都要有来头**。没在前面交代过的数字（「18」「2 MB」）读者会卡住；要么交代，要么删。
- **问题只属于某一种方案时，放在那种方案的模块里**，别放在总述里让读者以为都有这个问题。
- **用读者认得的具体例子，不用抽象符号**。几条线、几个点、几根小短条在动，读者不知道它们是什么（读者原话：「那 4 个进度条…我看不懂是什么意思」）。把它换成一件说得出来的事：谁、对谁、说了一句什么（「支付系统」的 Agent 问「数据平台」的 Agent「订单接口怎么调用？」，对方回「接口文档已发送」）；符号要用就用读者在前面已经见过的那个东西（刚才列表里的那几行），不要临时发明一个。一个例子演透，比三对抽象的往来强；例子好就再加一个不同的，不要把同一个例子重复三遍。
- **这一步用不上的层和对象不画**。「一层层出现」不等于每一层都要出现：讲「容器把内存还给虚拟机」时再画宿主机，读者要多认一层却什么也没多懂（读者原话：「不需要再体现宿主机了，有点复杂了」）。画之前问：去掉它，这一步的那句话还成立吗？成立就去掉。
- **讲完要回答「所以呢」**。每个模块的最后一步或结尾页写清：这对读者意味着什么、现在做到哪了（已上线 / 只在测试环境 / 还没做）。
- **深浅按读者定**。动手前写下「读者是谁、他已经知道什么、不关心什么」：对内行讲基础会被嫌啰嗦，对外行堆实现细节会被嫌太具体。

**文字**
- 每步：一句话（lead）+ 最多 2–3 条要点，**加粗**只给结论性的数字或词。左边字太多就删细节，细节放结尾页或图右下角的小注。
- **不引用后面才讲的东西**。「不再各存一份」「还是」「也一样」「那一份」这类话，指的东西必须已经在前面出现过。调整过章节顺序后，把挪到前面的那段文字**按新顺序从头读一遍**。
- 第一次出现的术语当场用半句话解释，全页同一个东西只用一个叫法。
- **页面上不出现内部名字**：RFC 号、PR 号、文件名、函数名、命令名、内部机器名。读者就是这段代码的开发者时例外。
- 术语和「数字 + 单位」不拆行：文字里包上 `{{ }}`，如 `{{4 KB}}`、`{{1,380 亿 token}}`。
- 页脚标「更新：年月 · 对着哪个版本的代码核的」。页面是那一天的快照，代码会变。
- 推断的、没实测的，写明「推断」「待实测」；别家的数字写清是谁的（「论文」「POC」「main 上」）。

**画面**
- **同一个东西全程是同一个对象**：数据块从磁盘「飞」进内存、再「飞」进虚机，而不是这里消失那里出现。读者靠它跟住过程。
- **颜色有固定含义**，全页一致（如：青 = 数据，紫 = 程序，橙 = 正在发生的动作，蓝 = 结论 / 还回去的）。图例只放用到的。
- **动作也有固定含义**，全页不换用法（如：橙线画出来 = 发出请求，色块飞过去 = 数据送到，橙圈 = 大家共用的那一份，整组变淡 = 用不上了）。同一类动作速度一致：路远的飞得久，不要都压成同一个时长。
- **状态用颜色说，而且只分两三种**：例如「蓝 = 正在用，灰 = 已释放」。读者一眼能数出有多少蓝、多少灰，后面「灰的被收走」才看得懂；同一种状态不要又用颜色又用图标又用文字各说一遍。
- **要读的字不动**：一句话要从 A 传到 B，就让这句话停在说话的一方旁边，沿线送过去的是一个小记号；读的是停着的字，看的是记号走的路。字跟着飞，读者两样都没看清。
- **先动、再停**：一步里的主要动作在前六成时间内做完，之后画面安静，留给读者读左边那句话；两个重要的动作不同时发生；大的移动不短于半秒，横穿整张图的不短于 0.7 秒，再快眼睛跟不上。
- **怎么来就怎么走**：线条画出来的框，退场时由线条收回去；飞进来的飞出去。全页的进出场只用两三种手法，淡入淡出不要成为默认。
- **几条线汇到同一个目标时，从不同方向进**（左端、顶部、右端各一条），不要并排落在同一条边上：迟早会重合，或者从别的图形后面穿过去（读者原话：「手机的线和客户端的线重合了，并且手机本身挡住了客户端的线」）。
- **意思对了但不好看，也算没做完**（读者对一朵云的原话：「意思对了，但是云太丑太生硬」）。关键的图形（全页反复出现的那个、最后一步落在上面的那个）先画两三种样子并排看，挑一个；看的时候问：线条和页面上别的东西是一个手感吗？比例舒展吗？和背后的线分得开吗？
- **强调标记（圈、箭头、橙色小字）讲到时才出现，讲完就退场**，最晚在下一步开头退掉，不带进后面的步骤。**每一步结束时的画面单独拿出来要说得通**（`step-NN.png` 就是这个画面）。
- 强调共用 / 同一份：多条箭头汇成一条落在同一个目标上，再加一个橙圈。
- 「省掉了」「还回去了」要演出来：东西飞到占用条上对应的那一段，**落定以后**那一段再缩短；不要边飞边缩。飞去的位置要和缩掉的那一段对得上。
- 示意和真实尺寸对不上时，标「示意」，并且别让示意的格子大小暗示一个不存在的单位。
- **框的嵌套和名字照真实归属**：动手前列一张「对象 → 它真实在哪个网络空间 / 容器 / 进程 / 服务里」的表。独立的容器或进程（sidecar、代理）画成并列的框，**不画进业务容器里**；外框写清它是什么（「某个容器组的网络空间」），框名用读者心里的叫法（「业务容器」，不是「主容器」）；同名的东西分清归属（两个服务各有一个叫 sidecar 的组件时，各用固定的全名），图上和左栏都别混用。
- **连线拐角越少越好**：端点落在两个框相对的边上，**不要瞄着框中心**；两框高度有重叠就一条直线；要拐只经一个明确的拐点（绕开障碍的 U 形最多两个），拐点避开文字；数据包、红线等走同一条路的东西共用这组拐点。小折弯会被读者当成「这里有什么特别的含义」。`check.js` 的 bends 项会拦。
- 说明小字贴在框的边上，不要压在框里的对象上。
- **图里的字不小于 14 个画布单位**。图在 13 寸笔记本上会缩到约 0.8 倍，再小就看不清；`check.js` 的 fontsize 项按 1280 × 720 下不小于 11px 来拦。放不下就删内容，不要缩字。模板另有「放大图」（顶部按钮 / F 键），那是给读者的选项，不是字小的补救。

## 3. 常见返工（收到这种反馈，直接这样改）

| 反馈 | 多半的原因 | 改法 |
|---|---|---|
| 「这一步动画没结束 / 结尾有问题」 | 关键帧排到了这一步结束之后，或淡入刚好卡在结束时刻 | 这一步的动作全部在 `T(id, 0.88)` 前开始、`T(id, 1)` 前停住；`check.js` 的 still 项会报 |
| 「字飞出框了 / 位置不对」 | 父框和里面的东西不是同一时刻开始动；多写了一帧只改颜色的关键帧，把位置钉住了 | 父子用同一组时刻；给它们标 `data-box` / `data-in`，用 contain 项逐帧查。**别拿别的指标（字号、透明度）代替「在不在框里」** |
| 「第 N 步和第 M 步看起来一样」 | 差别只写在文字里 | 把差别画出来（见上：汇聚箭头 + 圈） |
| 「哪来的 X？」 | 图上有个没交代的数字 / 单位 | 交代来源，或者从图上拿掉，只在「为什么」里提一句 |
| 「顺序不对，应该先 A 再 B」 | 没按因果 / 层次排 | 按「先底层后上层」重排这一步的时刻；**顺便把其它步骤也按同一条过一遍** |
| 「XX 就很奇怪，之前也没提过」 | 文字引用了后面才讲的东西 | grep「不再、各存、还是、也一样、那一份、对比」，逐处确认指的东西已出现 |
| 「字太多 / 看不清 / 太小」 | 细节堆在左栏；图里的字小于 14 | 删到一句话 + 要点；图里的字调到 14 以上、放不下就删；`check.js` 的 fontsize、text 项会报 |
| 「从首页滑下来第一步没动画 / 刷新后没动画」 | 改坏了引擎里的进入逻辑 | 别动 B2 段的 `enteredFirst`、`pendingShow`、起始那几行；`check.js` 的 wheel 项会报 |
| 「为什么会有这种拐角？」（附截图） | 箭头瞄着对方框的中心，或拐点各算各的，出现一小段来回折；同一条路的数据包和线各走各的 | 端点放在相对的边上，能直就直，最多一个拐点，数据包和线共用拐点；`check.js` 的 bends 项会报。**把全图所有连线按同一条过一遍** |
| 「X 是不是独立的 Y？画在 Z 里面合适吗？」「这块应该叫……是不是更准确？」 | 框的嵌套没照真实归属（把 sidecar 画进了业务容器），或框名用了内部叫法 | 先列「对象 → 真实归属」表再改嵌套；外框写清它是什么，框名改成读者的叫法；同类的框全图一起核 |

收到一条反馈后，**先想这条反馈在别的步骤是不是也成立**，一起改掉，别等对方一处处指。
