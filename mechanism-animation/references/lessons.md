# 反馈记录：规则是怎么来的

这套做法出自两页原理动画（分层文件系统 8 步、虚机内存 12 步），给同一位读者来回改了三十多轮；后面又有几页别的题目。下面按类记下读者的原话和当时的改法，SKILL.md 第 2、3 节的规则都出自这里。遇到规则没覆盖的情况，来这里找最像的一条。

## 形式

| 读者说的 | 当时错在哪 | 之后的做法 |
|---|---|---|
| （两次否掉静态分块图）要连续的动画 | 做成几块静态图之间切高亮 | 同一批对象跨步骤一直在、会移动；每步内部有动作，步与步之间有过渡 |
| 太慢、太线性，点步骤又一闪而过 | 把滚动条直接映射成时间轴 | 一次手势走一步，每步按自己的时长播完；点某一步 = 淡出、回到这一步开头、淡入、正常速度播一遍 |
| 「动画在刚开始滚动的时候就出现，有点突兀」 | 图在滚动途中就淡入 | 滚动停了图再出现，动画也等那时再开始 |
| 「我从首页向下滑动到 01 是没有动画的」「刷新后第一步动画没了」 | 进入第一个模块时直接显示了第 1 步的终态 | 从别处进到第一个模块，第 1 步从头播一遍；刷新后也播 |
| 「能不能把动画搞大一点？有点小看不清」 | 图被左栏挤小 | 加「放大图」模式：图占满屏幕，说明挪到图上方 |
| 「第一步跑到首页去了」 | 左栏上移时越过了本页上沿 | 上移量按本页自己的顶算，模块页 `overflow:hidden` |

## 讲法

| 读者说的 | 当时错在哪 | 之后的做法 |
|---|---|---|
| 「颠倒一下顺序，把容器放前面……容器是共享内存的，没问题，但如果换成很多虚机，就会造成内存的问题」 | 先讲出问题的方案，最后才讲没问题的 | 先讲没问题的情况，再讲出问题的，再讲解法 |
| 「这个浪费部分基本是 microVM 才存在的问题，不应该放在上面，不然读者会以为两种方案都存在」 | 把只属于一种方案的问题放进了总述 | 问题放在它所属方案的模块里 |
| 「应该是先出现宿主机，然后数据从磁盘到宿主机的内存，再出现单元，然后内存复制到单元，最后单元里才出现容器」「其他有没有类似的问题，也一起修了」 | 一开场所有框都在；程序先出现、数据后到 | 先底层后上层、先因后果，一层层出现；改一处后把所有步骤按同一条过一遍 |
| 「第 12 步的动画有点急了，应该是小块飘到宿主内存条上，然后内存条往回缩，而不是飘的同时往回缩」 | 两个有因果的动作同时发生 | 先落定，再缩；落点和缩掉的那一截对得上 |
| 「读者会想，哪来的 2 MB？」「到底是先按 2MB 再按 4KB，还是直接按 4KB？」 | 把默认行为单独演了一步，再演实际做法 | 主线只演实际做法；默认值放在「为什么要专门设」一句里，并写明来头 |
| 「第 10 步和第一步看起来一样，是因为……存在一样的内存问题吗？」→「可以画出来单元内部的容器直接共享单元的内存」 | 差别只写在文字里，画面一样 | 把差别画出来：读箭头汇到同一份上，加圈 |
| 「这个 18 的数字毫无来头」 | 图上放了一个没交代的数字 | 删掉；每个数字都要能说出来源 |
| 「如果是 6 个镜像，每个镜像里面有 3 层，那最后应该是 18 个只读文件，而不是 6 个」 | 示意图把「镜像」和「镜像里的层」画成了一回事 | 图里的个数要和真实的对应关系一致，分不清的两个概念先分清再画 |
| 「你不是说『所有只读层都走 pmem』吗？」 | 前后两处用了不同说法讲同一件事 | 同一件事全页只用一种说法 |
| 「前两步不需要红色箭头」「第四步刚开始有红框又消失，其实开始的时候不需要」 | 强调标记出现在还没讲到它的时候 | 圈、箭头只在讲到它的那一刻出现 |

## 文字

| 读者说的 | 当时错在哪 | 之后的做法 |
|---|---|---|
| 「左边的字太多了，不需要那么多细节」「mkfs 是什么？」 | 把命令名和实现细节写进了步骤说明 | 一句话 + 要点；术语要么解释要么不出现 |
| 「信息密度比较大，看一下如何增加易读性，比如分段、分块」 | 每步一大段话 | 拆成一句话 + 2–3 条要点，结论加粗 |
| 「『不再各存一份』就很奇怪，之前也没有提过各存一份。看一下还有没有类似的表述，都修复一下」 | 调了章节顺序，挪到前面的文字还在拿后面的内容作对比 | 调序后按新顺序重读；grep 回指的词 |
| 「不需要『最下面 2 层就是 base-b 的那几层（同一批）』这种东西」 | 用括号补充读者不需要的对应关系 | 删 |
| 「首页的介绍没有跟着改」 | 改了模块，开头页的预告还是旧的 | 改模块后同步改开头页和结尾页 |

## 画面

| 读者说的 | 当时错在哪 | 之后的做法 |
|---|---|---|
| 「字飞到框外面了」→ 修后「还是飞出框」（附截图） | 第一次只查了字号有没有变小，就回复「逐帧查过」；真因是外框多了一帧关键帧，位置被钉住，晚出发 | 直接查读者看到的那个关系：子元素在不在父框里，整段时间轴逐帧查；汇报自测时写明查的是哪个性质 |
| 「第 11 步的动画没结束」「第 12 步结尾有问题」 | 最后几个对象的关键帧排到了这一步结束之后 | 每步结束前全部停住；用脚本查「结束前一刻和结束时是否一样」 |
| 「宿主机内存条上有白色间断」「小格子飘到的位置不对，进度条收缩的时间也太早」 | 条上各段的位置各算各的；飞行落点写死 | 一个对象管整条的布局；落点用条的实时位置算 |
| 「能不能用蓝色到红色渐变来表示冷热」「让每一个块内部的小块消失，一整个作为一块上色」 | 细格子太多，颜色互相干扰 | 用不到细节的步骤，把细格合成整块 |
| 「宿主的内存应该不是被虚机占满的吧？」「层文件在哪里？你动画里演示的好像是在内存里」 | 示意画法暗示了不对的事实 | 示意也不能和事实相反：谁在磁盘、谁在内存、占多少，位置和比例要说得通 |
| 「那 6 个镜像是不是可以在中间加上竖的分隔线来说明是三类」 | 分类只靠颜色 | 分类用分隔线 / 分组框明示 |
| 「从上到下的横线看不清上面的字，而且它很快就消失了，看不懂它是什么意思」 | 装饰性的扫描线没有含义 | 没有明确含义的动效不要 |

## 事实

两页都在定稿后做过一轮只读技术核查（多个核查者逐条对代码和文档，加一个对抗审查者），文件系统那页查出 19 处（4 处真错），内存那页 17 处（3 处有误导）。真错的共同点：照着设计文档 / 论文写，而代码已经不是那样了。所以：**画之前先对代码核一遍；论文和默认值的做法要和「我们实际的做法」分开讲。**

## 定稿时的两轮外部意见

- **一位专做文档的同事看过草稿**，补的几条已并进规则：动画前先试「编号步骤 + 两三张定格图」；动画只管第一次看懂、不能当查阅材料，所以要有「全过程一览」并保留文字版；页面上不放内部名字；深浅按读者定；讲完回答「所以呢」；页脚标更新日期和核对的版本；中文术语和「数字 + 单位」不拆行；图里的字有最小实际字号；按 13 寸笔记本的两档尺寸验；动作和颜色一样有固定含义；强调标记讲完就退场、每步终态单独看得懂。
- **两个没有任何背景的 Agent 只凭这份 skill 各做了一页**（git 的 add / commit / push；DNS 解析），都在 1–2 轮自测内通过。它们卡住的地方已改：`span` 两个时刻挨得太近会报一串看不懂的数字；`contain` 没标记时显示 PASS 让人以为查过了；模板缺框、箭头、说明行、图例这几个最常用的封装；自测超过命令行工具缺省的 120 秒；分镜里没有地方记「这一步结束时留下什么」。


## 透明代理：现在 vs 新方案（11 步）

讲「容器的出网转发从容器里挪到容器外」，做了一页 11 步的对比动画（现在怎么出网 → root 怎么绕过 → 新方案 → 前提和边界）。读者看完说「画得很好，我大概懂了」，过程中被打回的点如下。

| 读者说的 / 遇到的 | 当时错在哪 | 之后的做法 |
|---|---|---|
| 「出网代理是不是 sidecar 容器？把它画在业务容器内部合适吗？」 | 把一个独立的容器画进了业务容器的框里，读者会以为它是业务容器里的一个进程 | 独立的容器 / 进程画成并列的框；画之前列「对象 → 真实归属」表 |
| 「所以第一块应该是『某个容器组的网络空间』，下面『主容器』应该改成『业务容器』，这样是不是更准确？」 | 外框没说清它代表什么（其实是两个容器共享的网络空间）；「主容器」是内部叫法；还多画了一层没含义的内框 | 外框写清它是什么；框名用读者的叫法；删掉没有含义的框 |
| 「为什么会有绿框这种拐角？」（附截图） | 代理 → 防火墙的线瞄着防火墙的框中心，中途来回折了一下；绕过路径拐了两次；数据包和线的拐点各算各的 | 两框高度重叠就一条直线；要拐只经一个拐点（`PX`），数据包、红线共用这组拐点；全图连线一起过了一遍；`check.js` 加了 bends 项 |
| 第 4 步的说明小字压着框里的对象 | 说明放在了框内 | 挪到框的边上 |
| （自己踩的）图例互相压住、有一段场景出现两遍 | 用脚本拼接 C 段时切片下标写反，一整段被复制了一份 | 从备份重拼并断言下标顺序；拼完查对象是否重复定义（engine.md「坑」） |
| 讲解（左栏和对话）里把两个服务各自的 sidecar 混在一起说 | 两个同名的组件分属两个服务、都在网络空间里，没先分清就开讲 | 同名组件先分清归属再画、再讲；图上和文字里各用固定的全名 |


## 一支介绍短片的反哺（纯代码做的视频，不是本模板的页面）

给一个多 Agent 协作平台做了一支 140 秒的介绍短片（一夜五版，读者按时间码逐条给了三十多条意见）。片子里讲机制的几段（消息投递、休眠释放内存、多个用户共用内存）和这里是同一门手艺，被打回的点和之后的做法如下，已并进 SKILL.md 第 1、2 节。

| 读者说的 | 当时错在哪 | 之后的做法 |
|---|---|---|
| 「从电脑里面冒出来的那 4 个进度条不太好看，我看不懂是什么意思」 | 用几条抽象的蓝色短线表示「Agent 还在运行」 | 换成读者已经见过的东西（列表里那几行 Agent 的名字标签） |
| 「可以体现一下具体点的场景，比如说一个 Agent 问另一个 Agent 的接口怎么使用」 | 「跨项目协作」画成三对负责人之间抽象的连线 | 演一问一答，字读得清；读者随后说「效果不错，再加一个」（方案发给另一个 Agent 评审） |
| 「不需要再体现宿主机了，有点复杂了」；容器迁移、对抗验证整段被删 | 机制有几层就画几层，有几个功能就讲几个 | 这一步的那句话用不上的层和对象不画；讲不透的功能宁可不讲 |
| 「正在生成的 Agent 都是蓝色，释放的内存都是灰色，这样就可以看到很多容器有蓝色内存和灰色内存，然后灰色内存归还」 | 状态靠小图标和小字区分，退远了看不出来 | 两种颜色说两种状态，先让读者数得出，再让其中一种被收走 |
| 「把那 4 个灰色的全清理掉」 | 只演了一个休眠，其余三个空闲的还留着，读者以为它们不会被清 | 例子演完后，同类的其余几个也要跟着走完，别留半截 |
| 「手机的线和客户端的线重合了，并且手机本身挡住了客户端的线」 | 三条线并排落到同一个目标 | 三条线从左端、顶部、右端三个方向进 |
| 「镜头拉远移动再拉近，看起来有点晕」 | 为了让读者看到两处，镜头来回跑 | 退到能同时看见两处的位置停住，只让线和消息动（分步页面没有镜头，对应的是：别让整张图来回平移缩放） |
| 「云的意思对了，但是云太丑太生硬」 | 关键图形只求表意 | 画三种并排挑；好看是要求，不是加分项 |
| （评审时指出，读者没说）字幕还没读完画面又动了；一拍里七个动作 | 动作排满整拍 | 先动、再停：主要动作在前六成做完，其余时间安静 |
| （第一次看的人测试）「负责人」被读成人而不是 Agent | 术语第一次出现没交代 | 找一个不知情的代理只看成品复述，它卡住的地方就是要改的地方 |
